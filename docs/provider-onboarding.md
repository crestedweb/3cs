# Provider onboarding setup

The provider profile is stored as structured JSON in `providers.profile_data`; account, verification and referral states use separate columns. Apply `supabase/migrations/202610090001_provider_onboarding.sql` before deploying this version. Provider evidence is stored in the private `provider-documents` bucket created by that migration. The server uses its Supabase service role for upload and short lived administrator download links; do not put that key in Vite/client environment variables. `PROVIDER_DOCUMENTS_BUCKET` is optional and defaults to `provider-documents`.

UK postcode lookup and place search are server-side calls to [Postcodes.io](https://postcodes.io/docs/overview/). It provides postcode coordinates and place search without an API key. If unavailable, an account can still be submitted for manual review; the server stores no guessed coordinates and radius matching stays unavailable until lookup succeeds. A provider must explicitly select the places it serves. Radius uses straight-line distance and does not represent road travel time.

CQC registration, locations, regulated activities and insurance are collected as self-declared data. They remain pending manual review and are never presented as independently verified. CQC publishes a [Syndication API](https://api-portal.service.cqc.org.uk/) with provider and location information; access requires a subscription key. This deployment has no CQC credentials or confirmed API subscription contract, so it does not claim to verify CQC records automatically. Configure and test the official API subscription before adding an integration; store credentials on the server only. CQC applies to relevant regulated services in England; the form records Wales (Care Inspectorate Wales), Scotland (Care Inspectorate Scotland), and Northern Ireland (RQIA) separately.

Providers may upload PDF, DOC, or DOCX files up to 5 MB. Uploads remain private and pending until an administrator opens them through a short lived signed URL and marks them reviewed or rejected. The JSON fallback has no private object store, so document upload is disabled when Supabase is not configured.

Provider dashboard sessions are opaque in-memory bearer tokens with a 12 hour lifetime. Admin sessions use signed bearer tokens with the same lifetime so they remain valid across API restarts. Set `ADMIN_SESSION_SECRET` to a long random value and keep it stable across deployments; when it is not set, the server uses the Supabase service role key or admin password as the signing secret. Configure `ADMIN_EMAIL` and `ADMIN_PASSWORD` for the local administrator account, or configure Supabase Auth roles as currently supported by the login route.

Provider profiles and sign-in accounts are separate Supabase records. Admin deletion now removes both. If a provider profile was deleted directly from the database or before this cleanup was added, the Auth account may still exist: the provider can restore the profile by registering with the same email and existing password. If they no longer know that password, an administrator must delete the matching provider account under Supabase Authentication > Users before the provider can register with a new password.

The provider login page includes a password-reset request and reset form. Configure `PUBLIC_APP_URL` on the server to the public website origin (for example, `https://www.3cscareservices.co.uk`) and add `{PUBLIC_APP_URL}/provider/reset-password` to the Supabase project's Authentication > URL Configuration > Redirect URLs. The Supabase recovery email template must retain its confirmation link so the recovery tokens are returned to this route. Keep Supabase API keys server-side; reset requests return the same response whether or not an account exists.

Provider Google sign-in is available only to email-verified Google accounts whose email matches an existing provider profile. Google sign-up authenticates the user first, then requires them to complete the existing provider onboarding form; no provider profile is created until that form is submitted. The server requires `SUPABASE_ANON_KEY` to start OAuth; it never places the service-role key in a browser redirect. To enable Google, create an OAuth client of type Web application in Google Cloud Console and add the Supabase project's callback URL (`https://<project-ref>.supabase.co/auth/v1/callback`) as an authorized redirect URI. In Supabase Authentication > Sign In / Providers > Google, enable Google and enter the client ID and client secret. Add both `{PUBLIC_APP_URL}/provider/google-callback` and `{PUBLIC_APP_URL}/provider/google-callback?mode=signup` to Authentication > URL Configuration > Redirect URLs, and set the server's `PUBLIC_APP_URL` to the deployed site origin. Do not expose the Google client secret or Supabase service-role key in the frontend.
